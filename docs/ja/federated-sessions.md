# フェデレーションセッションを上流と同期させる

ユーザーが[外部 IdP](oidc-federation) 経由でサインインすると、Authagonal は*独自の*セッションとトークンを発行します。既定では、そのローカルセッションはその後独立して存続します。顧客がディレクトリでユーザーを無効化したり、ゲストの共有リンクが上流で取り消されたりしても、ローカルの Authagonal セッションは Cookie の有効期限が切れるまで機能し続けます。

オフボーディングや取り消しをすばやく反映させるには、**`RevalidateOnRefresh`** を有効にします。すると Authagonal は、ローカルのトークンをリフレッシュするたびに上流のリフレッシュトークンを IdP で引き換え、上流がその資格情報はもう存在しないと応答した場合はローカルのリフレッシュを拒否します。こうしてセッションは、アクセストークン 1 つ分の有効期間のうちに新しいトークンを得られなくなります。

`RevalidateOnRefresh` は **OIDC 接続**だけの設定です。SAML には引き換えるべきリフレッシュトークンがないため、SAML 接続では再検証できません。そうしたセッションは、アサーション自身のセッション有効期限で上限を設けてください ([SAML](saml) を参照)。

## 有効にする {#enable-it}

接続ごとに設定し (以下のように設定ファイルから初期投入するか、[管理 API](admin-api) で接続を作成する際に設定します)、上流が実際にリフレッシュトークンを発行する必要があります。

```json
{
  "OidcProviders": [
    {
      "ConnectionId": "acme-entra",
      "MetadataLocation": "https://login.microsoftonline.com/<tenant>/v2.0/.well-known/openid-configuration",
      "ClientId": "...", "ClientSecret": "...",
      "AllowedDomains": ["acme.com"],
      "RevalidateOnRefresh": true
    }
  ]
}
```

セットアップはこれだけです。フラグが有効な場合、Authagonal は上流に要求するスコープに `offline_access` を追加し (下流のリクエストにまだ含まれていない場合)、上流が返したリフレッシュトークンを保管し、ローカルのリフレッシュのたびにサーバー間通信でそれを引き換えます。上流のリフレッシュトークンがクライアントに渡されることは**決して**ありません。トークンはセッションごとの永続ストアに暗号化して保存され、ログイン時に一律 7 日間の有効期限 (セッションの絶対上限) で保存され、再検証にのみ使われます。

上流側の協力が必要です。上流のアプリ登録が `offline_access` を受け取らない場合 (たとえば同意が付与されていない場合)、リフレッシュトークンは返されず、引き換えるものがありません。その状態では、Authagonal はリフレッシュのたびに警告 (`RevalidateOnRefresh is enabled for connection ... but no upstream refresh token is held`) をログに出力し、上流への再確認は**行われません**。

## リフレッシュ時に起こること {#what-happens-on-refresh}

1. RP は通常どおり Authagonal のトークンをリフレッシュします (`/connect/token` での `grant_type=refresh_token`)。
2. Authagonal は IdP のトークンエンドポイントで上流のリフレッシュトークンを引き換えます。
   - **成功** → ローカルのリフレッシュが進みます。上流がトークンをローテーションした場合は新しいトークンが保存され、セッション内のすべての RP グラントで共有されます。
   - **`invalid_grant`** → フェデレーションの資格情報が失われています (ユーザーの無効化、セッションの取り消し、トークンの失効)。ローカルのリフレッシュは**拒否**されます。RP は `/connect/token` から `invalid_grant` を受け取り、保存されていた上流のトークンは削除されます。この拒否で失敗するのはそのリクエストだけで、Authagonal のグラントは取り消されません。そのため RP のリフレッシュトークンは消費されずに残り、上流で取り消されている間は拒否され続けます。
   - **その他の 4xx** (たとえばローテーションされた、または設定を誤ったシークレットによる `invalid_client`、あるいは 429)、5xx、解析できないエラーボディ、通信障害、または読み込めない接続 (削除済み、ディスカバリやシークレットの失敗) → **一時的**なものとして扱われます。オペレーターの設定ミスでフェデレーションユーザー全員が一斉にログアウトされることがないよう、セッションは維持されます。設定を修正すれば、何も失われません。セッションには引き続きセッションの絶対上限が適用されます。

上流のトークンはブラウザセッションごとに **1 つ**だけ (ユーザー + 接続 + セッションをキーとする) なので、ユーザーが開いた 2 つ目の RP は*同じ*トークンを読み取ってローテーションします。そのため、あるアプリのリフレッシュによって、別のアプリが失効したコピーを持ったまま取り残されることはありません。

## 実装するものはない {#nothing-to-implement}

ここで書くべきインターフェイスはありません。永続ストア (`IUpstreamRefreshTokenStore`) は Azure、AWS、SQL の各ストレージプロバイダーによって自動的に登録され、引き換えは内部で行われます。取り消し可能な資格情報を上流が持っている接続で、`RevalidateOnRefresh` を有効にするだけです。

保存されたトークンは、セッションがどの経路で終了した場合でも、その経路がトークンに到達する限り削除されます。サインアウト、アカウントページからのセッションの取り消し、「すべての場所からサインアウト」、有効期限切れの一掃処理です。ホストがストアを登録していない場合は、セッション Cookie に含まれるコピーがフォールバックとして使われます。

OIDC フェデレーションのセッションはすべて、その接続が再検証を行うかどうかにかかわらず、どの接続がそのセッションを所有しているか (`upstream_connection_id` クレーム) も記録します。これは記録のためだけのもので、フラグのない接続については何も引き換えられません。

> **適用範囲:** この機能は、ストアが登録されている場所 (Azure Table、DynamoDB、SQL の各プロバイダー) であればどこでも有効です。**信頼できる**上流、特にリフレッシュトークンを 1 回限りでローテーションする上流 (Entra、Auth0) への接続で有効にし、サードパーティの IdP では `IsExternalConnection` と組み合わせてください ([セルフサービス SSO](self-service-sso) を参照)。

## 補完策: セッションの厳格な上限 {#complementary-a-hard-session-cap}

`RevalidateOnRefresh` は、上流での取り消しにセッションを確実に追従させます。それとは別に (あるいはそれに加えて)、ローカルセッションが上流で表明されたセッションより*長く存続しない*ようにしたい場合は、`SessionExpClaim` に有効期限 (Unix 秒) を含む id_token クレームの名前を設定します。Authagonal は、ローカルセッションと、そこから発行されるすべてのトークン (リフレッシュによるローテーションや、そのセッションを通じて承認されたデバイスコードグラントを含む) をその期限に制限します。[OIDC フェデレーション → セッション有効期間の上限](oidc-federation)を参照してください。

デバイスフローを特に挙げるのは、最近まで例外だったからです。デバイスコードのレコードには承認したセッションの期限を保持する場所がなかったため、フェデレーションセッションを通じて承認されたデバイスは、そのセッションが終了した後も、クライアントのリフレッシュの絶対有効期間いっぱいまでトークンを発行し続けていました。また、`RevalidateOnRefresh` がそのデバイスについて上流に再確認することもありませんでした。現在はどちらも承認したセッションに従います。*フェデレーションでない*セッションを通じて承認されたデバイスには引き継ぐべき期限がありませんが、これは認可フローの場合と同じ結果です。
